# Разработка AI Companion через Codex и Claude Code

## Цель и текущие границы

Олег — компаньон для одиночного Minecraft Java 1.21.1: общается по-русски,
помогает добывать и переносить ресурсы, создавать предметы, строить дома по схемам
из `mods/oleh_ai_schemas` и сражаться. Важен наблюдаемый результат в настоящем мире: нужные материалы
в инвентаре, достижимый маршрут, выполненный рецепт, полученный игроком предмет.
Полностью самостоятельная игра пока вне реализованных возможностей.

OpenRouter отвечает за свободный диалог и предложения планов; Inworld — за голос.
Прямые команды и многие проверки доступны без этих сервисов. Долговременная
цель в `CompanionGoals` пока поддерживает конкретный сценарий каменных кирок
для компаньона и игрока; это не универсальный планировщик любых целей.

Закреплённый стек указан в `gradle.properties` и `build.gradle`:
Java 21, Minecraft 1.21.1, NeoForge 21.1.262. Номер версии мода (`mod_version`)
меняется только по явному указанию владельца. [README](../README.md) описывает установку и управление.

## Один источник правил для двух помощников

[AGENTS.md](../AGENTS.md) хранит общие ограничения и рабочие правила.
[CLAUDE.md](../CLAUDE.md) импортирует его через `@AGENTS.md`.
Так не нужно вручную синхронизировать две копии инструкций. Открывайте помощника
в корне репозитория. Ссылки на это руководство в AGENTS.md обычные: нужный раздел
читается по задаче, а весь документ не импортируется автоматически.

При переходе со старого `CLAUDE.md` сначала перенесите актуальные ограничения
в общий файл: публикация только по отдельной команде, запрет платных проверок
без разрешения, согласованные предел ответа OpenRouter и история диалога.
Частные имена, локальные пути, переписку и отчёты переносить в публичные правила не нужно.

Публикация исходников, выпуск JAR и установка в Minecraft — отдельные действия.
Исправление или одобрение результата не разрешает отправку на GitHub.
Без нового номера версии по прямой команде владельца сохраняйте `mod_version`;
для нескольких выпусков одной версии используйте различимые названия/теги с датой.
Локальный `GITHUB_PUBLICATION.md`, если он есть, содержит порядок безопасной
публикации и не отправляется в репозиторий. Новый JAR собирайте из конкретного
публикуемого коммита; не берите оставшийся файл от прежних исходников.

Сами принципы работы — в разделе «Как работать» AGENTS.md; здесь они не повторяются.
Подход адаптирован из [Karpathy-Inspired Claude Code Guidelines](https://github.com/multica-ai/andrej-karpathy-skills):
это интерпретация наблюдений Карпатого сообществом, а не инструкция его авторства.
Механика файлов сверена с документацией [Codex](https://developers.openai.com/codex/guides/agents-md/)
и [Claude Code](https://code.claude.com/docs/en/memory#import-additional-files).

Путь поручения от чата до сообщения игроку описан в AGENTS.md.
Долговременная цель использует ограниченные навыки.

`client/` содержит и настоящие клиентские классы, и общую логику планов.
Например, сервер регистрирует `CompanionServerPlanPort.tick`, а GameTest используют
`CompanionPlanRunner`. Нельзя определять сторону исполнения только по папке.

При добавлении действия проверьте всю цепочку: список и параметры в codec,
описание инструмента в OpenRouter, прямую команду при необходимости, нормализацию
запроса, серверное исполнение, ожидание результата, отмену и регрессию.
Существующие тесты ищите по имени действия и механики, а не только по имени класса.

## Выбор проверок

Все команды ниже запускаются из корня репозитория. Нужен JDK 21; для первой
загрузки Gradle, NeoForge и остальных зависимостей нужен интернет.
Примеры для PowerShell; для Gradle-команд на Linux/macOS используйте `./gradlew` вместо `.\gradlew.bat`.
Сценарии `.ps1` рассчитаны на Windows и вызывают `gradlew.bat`.

| Изменение | Проверка |
| --- | --- |
| Документация и инструкции | Проверить пути, команды и `git diff --check`; игровой запуск не требуется |
| Java, ресурсы или сборка | `.\gradlew.bat build` плюс подходящая проверка поведения |
| Игровая механика, планы, навигация | `.\gradlew.bat runGameTestServer`; учитывать длительные сценарии |
| Очередь и отмена задач | `.\scripts\verify-tasks.ps1 -Repetitions 1` |
| Сохраняемая цель | `.\scripts\verify-goals.ps1 -Repetitions 1` |
| Цель при настоящем перезапуске сервера | `.\scripts\verify-goal-restart.ps1` после создания `build/diagnostics/` |
| Самостоятельные реплики и соответствующая обработка команд | `.\scripts\verify-banter-tools.ps1 -Repetitions 1` |
| Тихая работа, речь и восстановление поручений | `.\scripts\verify-quiet-work.ps1` |
| Критические проверки длительной работы | `.\scripts\verify-endurance.ps1 -CriticalOnly -Repetitions 1` |
| Длительные сценарии леса, пещеры или перезагрузки | `.\scripts\verify-endurance.ps1 -Arena Forest -Repetitions 1`; варианты арены: `Cave`, `Reload` |
| Полный набор с итоговым JSON | `.\scripts\verify-scenarios.ps1 -Repetitions 1` |
| Экран задач | `.\scripts\verify-task-ui.ps1` и просмотр созданных снимков |
| Прочие экраны, рендер, клавиши | `.\gradlew.bat runClient`, ручная проверка изменённого сценария |
| Живой диалог, STT/TTS | Ручная проверка с собственными ключами только по отдельному разрешению на платные запросы; локальные GameTest не доказывают работу провайдера |

Для проверки перезапуска заранее выполните `New-Item -ItemType Directory -Force build/diagnostics | Out-Null`:
сам скрипт создаёт отдельный тестовый мир, но не создаёт каталог журналов.
Остальные сценарии могут запускать долгие серии: явно задавайте число повторов,
когда у скрипта есть параметр `Repetitions`. Одна успешная серия не доказывает
стабильность многочасовой игры.

`build` компилирует и упаковывает мод, **GameTest он не запускает**.
Тесты находятся в `src/main/java`, а не в обычном `src/test/java`; не объявляйте
проверку игровой механики успешной по пустой стандартной задаче `test`.
Тестовые классы и структуры исключаются из итогового JAR в `build.gradle`.

Полный `runGameTestServer` включает endurance/marathon-сценарии; названия тестов
с «часами» не равны измеренной длительности запуска. Для механических GameTest
ключи OpenRouter/Inworld не нужны. Сценарии с `--offline` сначала требуют
успешной загрузки зависимостей; при отсутствии кеша начните с обычного `build`.

Выборочные скрипты временно заменяют аннотации/исходники тестов и создают
структуры в `src/main/resources`. Они возвращают исходный текст в `finally`.
Запускайте их последовательно, без редактирования затронутых файлов или параллельной
сборки в этом checkout. После принудительного прерывания проверьте `git diff` и
временные каталоги; не восстанавливайте файлы вслепую поверх чужих изменений.
Отчёты обычно находятся в `build/diagnostics/`; UI-сценарий складывает снимки
в `build/tasks-client/screenshots/`.

При исправлении сначала получите воспроизводимый сбой или явное наблюдение.
Добавьте небольшую регрессию в подходящий существующий набор, если поведение
можно надёжно проверить. Проверяйте состояние мира и инвентаря, а не только текст
«успешно». Утверждения о сохранении после перезапуска проверяйте отдельным
процессом; одна сериализация в памяти этого не доказывает.

## Передача задачи между помощниками

Одна задача — одно изменение с понятным результатом и проверкой. При переходе
между Codex и Claude передайте цель, затронутые файлы, важное принятое решение,
выполненные команды с результатом и оставшуюся работу. Для небольшой задачи
достаточно сообщения; для длинной можно использовать описание PR или issue.
Не создавайте постоянные журналы на каждый диалог.

Для одновременной работы используйте отдельные ветки и worktree. Ветки без
отдельных рабочих каталогов не изолируют изменения. Не запускайте выборочные
скрипты в одном каталоге из двух помощников одновременно.
После объединения изменений повторите затронутые проверки.

В PR сообщайте проблему и результат для игрока, затем доказательства проверки
и оставшиеся ограничения. Другой помощник полезен для отдельного review:
проверить выполнение условий, отмену, сохранение и побочные эффекты по diff.
