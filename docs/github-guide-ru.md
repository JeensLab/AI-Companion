# GitHub: памятка владельцу

## Основные вкладки

- **Code** — исходные файлы. Зелёная кнопка **Code → Download ZIP** скачивает исходники, а не готовый мод.
- **Issues** — ошибки, идеи и обсуждение задач.
- **Pull requests** — предложенные изменения, которые ещё не вошли в основную версию.
- **Actions** — автоматическая проверка сборки. Зелёная отметка подтверждает только выполненные проверки, а не отсутствие всех ошибок.
- **Releases** — опубликованные сборки. Для установки игрокам нужен файл `aicompanion-0.0.2.jar` из **Assets**.

## Как принять чужое обновление

1. Откройте **Pull requests** и выберите предложение.
2. Прочитайте описание во вкладке **Conversation**.
3. Во вкладке **Files changed** посмотрите изменения: красные строки удаляются, зелёные добавляются. Особое внимание уделяйте сетевым запросам, настройкам, зависимостям и файлам `.github/workflows`.
4. Проверьте результат **Actions**. При необходимости попросите автора исправить проблему в комментарии.
5. Для принятия чужого предложения откройте **Files changed → Review changes → Approve → Submit review**. Если автор затем изменит код, потребуется повторное одобрение.
6. Нажмите **Merge pull request** и подтвердите. После этого обновление попадёт в основную ветку.
7. Если обновление не подходит, нажмите **Close pull request** без объединения. Основной проект не изменится.

В этом репозитории для основной ветки включены проверка сборки и одобрение владельцем. Автоматическое объединение отключено. Владелец сохраняет административное право обхода правил; используйте обычную проверку предложений.

Запуск автоматических проверок чужого Pull Request также может ждать вашего разрешения **Approve and run**. Эта кнопка только запускает проверки и не принимает изменения в проект.

Обычным участникам не нужно выдавать роль **Write** или **Admin**. Они делают **Fork**, меняют свою копию и присылают **Pull Request**. Принятие PR обновляет исходники; уже установленный у игроков JAR автоматически не меняется.

## Как выпустить сборку

После принятия изменений соберите проект с JDK 21: `.\gradlew.bat build` на Windows или `./gradlew build` на Linux/macOS. Готовый файл находится в `build/libs/`.

Откройте **Releases → Draft a new release**, выберите нужный коммит/тег, напишите изменения и прикрепите только проверенный JAR. Затем опубликуйте выпуск. Не прикрепляйте всю папку Minecraft, конфиги, журналы или архив рабочего проекта.

Номер версии остаётся **0.0.2**, пока владелец явно не решит его изменить. Последующие изменения под тем же номером желательно описывать датой и списком изменений, чтобы различать сборки.

## Конфиденциальность

Код публичного репозитория доступен всем, как и его история. Логин GitHub, публичный профиль и публичные действия на GitHub также видны. Не указывайте в профиле сведения, которые хотите сохранить в тайне.

В **Settings → Emails** личного аккаунта можно включить **Keep my email addresses private** и **Block command line pushes that expose my email**. Для локальных коммитов используйте предоставленный GitHub адрес `noreply`, а не личную почту.

Ключи OpenRouter/Inworld вводятся в самой игре и не должны попадать в репозиторий. При проблеме с игрой сначала удалите личные сведения из отчёта; не публикуйте полные журналы переписки.

Официальные инструкции: [предложение изменений из своей копии](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork), [адреса электронной почты в коммитах](https://docs.github.com/en/account-and-profile/concepts/email-addresses).
