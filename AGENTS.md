# AI Companion: правила разработки

Общие инструкции для Codex и Claude Code. `CLAUDE.md` импортирует этот файл;
общие правила меняйте здесь, чтобы у помощников был один источник инструкций.

## Проект

Олег — русскоязычный ИИ-компаньон для одиночного Minecraft Java.
Стек: Java, NeoForge, Gradle Wrapper. Диалог и планы — OpenRouter,
распознавание и озвучка — Inworld. Прямые команды и игровая механика могут
работать без провайдеров. Мод помогает игроку в рамках реальных ресурсов мира.

- Версии Minecraft, NeoForge и мода — в `gradle.properties` (`minecraft_version`,
  `neo_version`, `mod_version`); версия Java — в `build.gradle`.
- Текущая версия мода — **0.0.1**. Проект не пересоздавать.
- Менять номер версии только по явному указанию пользователя. Не повышать его
  автоматически при исправлениях, новых возможностях или пересборке.
- Не менять версии Minecraft, NeoForge, Java, зависимости и лицензию попутно с другой задачей.

## Публикация на GitHub

- По умолчанию все изменения, исправления, сборки и локальные коммиты остаются
  на компьютере пользователя.
- Отправлять изменения на GitHub, создавать или обновлять удалённые теги,
  публиковать или заменять JAR в Releases только по отдельной прямой команде
  пользователя на конкретную публикацию. Запрос на новый выпуск без указания
  номера не разрешает повышать `mod_version`; сборки одной версии можно различать датой.
- Просьбы исправить, доработать, собрать, проверить или установить мод локально
  не являются разрешением на публикацию. Одобрение результата работы также
  не означает разрешение загрузить его на GitHub.
- Предыдущее разрешение на публикацию не распространяется на последующие
  изменения или версии. Не включать автоматическую отправку и автоматический
  выпуск без отдельного прямого указания пользователя.
- Перед разрешённой публикацией проверить исходники, содержимое JAR и историю,
  которую предстоит отправить, на ключи и личные данные. Не отправлять конфиги,
  журналы, миры, частные инструкции и прежнюю локальную историю целиком.
  Следовать `GITHUB_PUBLICATION.md`, если он есть в локальной рабочей копии;
  этот файл с локальными путями не предназначен для общего доступа.

## Согласованные ограничения OpenRouter и Inworld

- Не делать платные запросы к OpenRouter/Inworld ради проверки без отдельной
  прямой команды пользователя. Для сборки и механических GameTest ключи не нужны.
- Сохранить установленный предел полного ответа OpenRouter **90 секунд**
  и историю диалога без старых снимков игрового состояния. Не менять их
  без новой прямой просьбы пользователя.
- Не переделывать связь с OpenRouter, очередь запросов и обработку ключей
  из-за прежнего уже устранённого эпизода: сначала нужен воспроизводимый
  текущий сбой или прямая команда пользователя на такую работу.
- Модель OpenRouter внутри мода и помощник-разработчик — разные системы.

## Как работать

- Найдите затронутый путь выполнения и существующие тесты; существенные допущения
  назовите в ответе. Уточняйте только выбор, который даёт заметно разное поведение
  для игрока и не следует из запроса, кода и тестов. Обратимые технические детали
  решайте сами; не превращайте каждый шаг в согласование.
- Делайте самое простое полное решение на существующих механизмах: без новых
  зависимостей, универсальных слоёв, настроек и запасных режимов «на будущее».
- Каждая изменённая строка относится к задаче: без попутного форматирования,
  переименований и переписывания соседнего кода. Удаляйте то, что стало
  неиспользуемым из-за вашей правки; прочие находки опишите отдельно.
- Исправляя поведение, по возможности сначала воспроизведите сбой тестом.
- Перед правками проверьте `git status`; сохраняйте чужие незавершённые изменения.
  Не заводите для небольших задач отдельные планы, журналы и файлы процесса.
- Сохраняйте проверенные этапы локальными коммитами без посторонних изменений;
  локальный коммит не является разрешением на отправку в GitHub.
- Если в локальной копии есть `HANDOFF.md`, `docs/README.md` или
  `docs/specification-adaptation.md`, используйте относящиеся к задаче разделы
  для сохранения принятых решений. Не публикуйте их автоматически: локальные
  материалы могут содержать личные пути и историю работы.
- Язык: с пользователем, в документации и PR — по-русски. Комментарии в коде
  и сообщения коммитов — по-английски, как в существующем коде. Реплики и сообщения
  для игрока — по-русски, строками в Java рядом с использующим кодом, как в соседних
  классах; `lang/*.json` — только для ключей регистрации, клавиш и настроек.

## Где искать код

Пути Java ниже относительны к `src/main/java/dev/aicompanion/`.

Путь поручения: чат → прямая команда (`client/CompanionLocalCommands`) или OpenRouter
(`client/OpenRouterClient`) → проверка плана (`client/CompanionPlanCodec`) → очередь
(`client/CompanionTaskQueue`) → `client/CompanionPlanRunner` → `client/CompanionServerPlanPort`
→ серверная механика (`entity/`) → результат с фактами (`entity/CompanionActionResult`)
→ сообщение игроку. Сохраняемая цель `entity/CompanionGoals` живёт на сервере отдельно.
Игровые регрессии — `gametest/` и `entity/CompanionStairApproachTests.java`;
структуры — `src/main/resources/data/aicompanion/structure/`.

Несмотря на имя папки, `CompanionPlanRunner`, `CompanionServerPlanPort` и часть других
классов `client/` используются сервером и GameTest. Проверяйте зависимости;
не добавляйте в общий путь импорты `net.minecraft.client.*`.
Таблица «задача → файлы», карта проверок и порядок работы: [docs/development.md](docs/development.md).
Читайте нужный раздел по задаче; не загружайте всю документацию перед каждой правкой.

## Условия корректности

- Ответ модели считается недоверенными данными. `CompanionPlanCodec` проверяет
  весь план до исполнения; при ошибке проверки ни один шаг не запускается.
  При новом действии согласуйте схему, проверки, выполнение на сервере и тесты;
  одной правки промпта недостаточно.
- Мир, сущность и инвентари меняются на серверном потоке; UI — на клиентском.
  Сетевые запросы и ожидание ответа не должны блокировать игровой tick.
- Ресурсы, рецепты, перенос и выдача предметов должны быть настоящими.
  Не обходите ограничения созданием предметов, телепортацией или фиктивным успехом.
- Добыча и передача вещей используют физический дроп и подбор; сохраняйте
  видимые удары, жесты, звуки и ход выполнения. Анимация не заменяет результат.
- Принятие поручения (`ACCEPTED`) не подтверждает завершение. Не определяйте
  завершение только по `CompanionActionResult.success()`: этот метод возвращает
  `true` и для `ACCEPTED`. Итог опирается на серверный результат и факты,
  связанные с нужным `workId`/операцией.
- Сохраняйте отмену, ограниченные повторы, таймауты и сброс при смене мира.
  Старый ответ модели не должен запускать отменённое поручение.
- Для изменений NBT и долгих задач учитывайте загрузку старых сохранений,
  прерывание и повторный запуск без дублирования ресурсов или выдачи.
- Отмена, смена задачи и перезагрузка не должны терять вещи или создавать
  второго компаньона; сохраняйте совместимость существующих миров.
- Ключи OpenRouter/Inworld хранятся только в локальных настройках Minecraft.
  Не помещайте их в исходники, журналы, документы, архивы, чат и отчёты проверки.
- Не публикуйте ключи, локальные настройки, аудио, миры и полные журналы.
  Диагностика может содержать диалог, координаты и инвентарь; см. `SECURITY.md`.

## Проверка и передача результата

- Сборка: Windows `.\gradlew.bat build`; Linux/macOS `./gradlew build`.
- Игровые тесты: `.\gradlew.bat runGameTestServer` или `./gradlew runGameTestServer`.
  **`build` не запускает GameTest.** Для выбора сценария используйте таблицу в руководстве.
- Некоторые `scripts/verify-*.ps1` временно переписывают тестовые исходники.
  Запускайте их последовательно; не редактируйте эти файлы и не запускайте сборку
  из другого процесса в том же checkout во время проверки. После прерывания
  проверьте восстановление затронутых файлов к состоянию перед запуском,
  включая прежние незакоммиченные правки. Не восстанавливайте их вслепую из `HEAD`.
- До финального ответа проверьте `git diff --check` и перечитайте diff.
  Не запускайте полный игровой набор ради документации; для неё достаточно
  проверить ссылки, команды и diff. Повторы нужны при нестабильности или
  изменениях, которые могут повлиять на результат.
- Сообщите, что изменилось для игрока/разработчика, какие проверки выполнены
  и что осталось непроверенным. Различайте чтение тестов, сборку, GameTest,
  ручную проверку в игре и проверку живого провайдера. При сбое укажите причину.

## Локальная установка после обновления

- После изменения мода, успешной сборки и подходящих проверок по умолчанию
  устанавливайте актуальный JAR в согласованную папку `mods` Minecraft без
  отдельного подтверждения. Локальный путь указан в `GITHUB_PUBLICATION.md`.
  Исключение — явная просьба пользователя не устанавливать эту сборку.
- Устанавливайте при закрытом Minecraft. Если игра запущена, не закрывайте её
  принудительно: попросите пользователя выйти, затем завершите установку.
- Перед заменой сохраняйте прежний JAR вне `mods` в `dist/installed-backup/`.
  Проверяйте SHA-256 резервной копии и установленного файла; в `mods` должна
  остаться одна версия JAR этого мода. Не меняйте миры, настройки и другие моды.
- Для изменений только документации переустановка не нужна.
- Локальная установка не разрешает публикацию: отправка на GitHub, удалённые
  теги и Releases — только по отдельной прямой команде пользователя на конкретную
  публикацию. Автоматическую публикацию не включать.
